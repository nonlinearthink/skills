# 质量与交付闭环

## 固定完整任务范围

从接入时记录的基准核验当前任务的累计变更：已提交、暂存、未暂存、新文件、删除及重命名。接手分支用用户给定的比较点或实际目标分支的 merge-base，不以开始接手的 HEAD 丢弃此前工作。基准不明确且会改变审查范围时先调查，仍不能确定才问。

已有他人改动保持其归属。若文件同时承载已有改动和本任务修改，保留前后内容作比较，提交前逐项核对；难以可靠分离时使用隔离 worktree 或报告冲突。验证运行环境包含已有工作时明确说明。

## 按行为选测

1. 将每项验收与受影响约束对应到检查：用户经过的调用/接口、依赖消费方、错误与重试、存储或构建边界。选能观察这些行为的最低必要成本检查。
2. 读取项目测试地图与脚本。已安装 `using-regression-testing` 时加载其选测方法；未安装时依据实际调用和契约追踪，不把该可选补充技能作为阻塞。
3. 开发中跑直接相关检查；交付前满足项目要求的核心和影响模块。明确要求或跨域影响无法限定时做全量，避免给所有任务机械追加全套重检查。
4. 缺陷重新运行原复现；新行为给可观察证据；界面/交互在可用的真实产品环境验证；构建和类型检查不能代替运行行为。无匹配或零用例不能算通过。
5. 记录命令、覆盖、结果和代码标识。未执行、失败、依赖环境缺失分别记清；已有结果只在相关代码、配置、依赖和环境未变时复用。

## 独立审查与修复

准备一个只读审查包，存临时目录或已有任务目录：

- 目标、验收、范围和已确认决定的指针。
- 固定基准、当前分支/HEAD、累计提交列表。
- 完整任务 diff；未提交和新文件也要提供内容，二进制给可检查产物。`git diff <base>...HEAD` 只够覆盖已提交部分。
- 初始已有改动的归属，避免把别人的代码算作本次实现。
- `AGENTS.md`、`CLAUDE.md`、`CODING_STANDARDS.md`、`CONTRIBUTING.md` 等实际适用标准、测试结果及环境缺口。
- 被审文件内容/完整补丁的摘要或哈希，用来识别审查后的变化。

读取 `code-review`，使用 upstream 适配规则。分派 fresh reviewers：Standards 检查项目标准和上游 smell baseline；Spec 检查缺失、错误、范围漂移及验收证据。两个结果保持分开。审查者只读，基于实际代码和验收，不以实现者总结代替证据。

对每项有依据的问题修复，或说明其不成立的具体证据；单纯“代理一致同意”不算证明。修复后重跑失效检查，并让独立审查者复核相关变更与原问题。新改动若扩大范围，更新完整审查包；测试和审查都通过才进入 ready 交付。

审查调用返回报告才算完成。宿主工具名或子代理数量不同可调整调度；独立性和完整范围是保留的要求。

## 交付至指定终点

- **只调查/设计/审查：** 交付对应回答、设计或发现；后续实施保持用户给定边界。
- **本地修改/补丁：** 交付实际文件与证据。未要求的提交、push、PR 不属于该终点。
- **默认 PR：** 验证和独立审查通过后，检查将提交的内容，按仓库约定与 trailer 提交到任务分支，push 到核验过的目标仓库并创建或更新该任务 PR。实际创建前确认 remote、目标分支和当前提交；受保护分支通过正常 PR 流程交付。原授权覆盖这些操作时继续，不重复问许可。
- **已授权自动合并：** 在上述基础上，读取当前 PR head、CI 和评审状态，满足平台门禁才合并；合并后读取平台确认状态。授权不能由“无人值守”或“别停”自动推导，也不包含部署。

PR 正文按项目模板，适用时读取 `pr`。先把问题、最终行为、验证和风险写完整，再发布；CLI 长正文用文件参数，保留换行。审查/验证尚有缺口时可按授权提交 draft，明确尚未 ready。

若没有 remote、认证、独立审查能力或必要环境，先完成所有独立的本地实现、可用验证和 PR 草稿，随后报告精确阻塞及可继续的动作。区分“代码完成”“验证完成”“独立审查完成”“PR 已创建”；默认终点未到时保持未完成，不能换个名字宣告成功。

新 push/rebase、冲突解决或底层依赖变化后，核对测试与审查覆盖的代码是否改变。仅迁移 commit 元数据且内容未变可复用内容审查；运行验证还要考虑环境、集成基准和配置。交付时给出当前产物的证据，不沿用失效绿灯。
