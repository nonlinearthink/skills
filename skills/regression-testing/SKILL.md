# 变更影响面与回归选测

把变更转换成可执行、可审计的回归计划：每项改变的行为和需要继续成立的约束都有检查，传播在有证据的边界停止。默认只选择影响面内的用例；项目要求的核心或全量门禁单独列出，不伪装成影响面结论。

任务只要求分析时交付计划；要求实现或验证时，按授权补充测试并执行可行检查。未执行、失败和证据缺口不能记为通过。

## 读取项目策略

先查仓库指南、测试地图、包脚本和测试配置，遵循用户及项目已有的验证要求。本 skill 不自动豁免全量、发布或外部操作规则。

区分两个维度：

- **回归范围**：核心回归是固定的最小发布关键行为集；模块回归覆盖本次改变的行为及受影响消费方；全量回归是项目约定的完整受控测试集。
- **执行方式**：单元、接口、浏览器、数据库、跨进程、运行时和安装包等。按要观察的边界选择方式，核心行为可能需要集成测试。

日常修改通常只跑直接影响与受影响消费方用例；合并、发布按项目策略叠加核心或全量门禁。项目没有测试地图时，从实际代码、测试和任务配置推导本次计划，并标明未确认的核心清单。建立、补齐或更新测试地图时，使用 [项目测试地图模板](references/project-test-map.md)。

## 1. 固定变更与回归入口

1. **固定比较范围。** 使用用户指定的比较点；分支审查通常用与目标分支的 merge-base，单次修改可用工作区开始前的状态。纳入范围内提交、暂存、未暂存、新增和删除文件；有并行工作时标明归属及运行时实际包含的改动。记录基准和当前状态，避免只看最新 commit。
2. **收齐改动说明。** 从需求、提测信息和 diff 确认改动模块与类型、公共组件、数据库/配置/权限/开关变化、建议验证点和回滚方式。缺失信息先从代码与仓库记录查证，仍未知的列入缺口。
3. **检查正式回归入口。** 核对版本与配置、环境和依赖服务、测试数据、账号与权限。局部开发检查可先做可行部分；入口未满足时明确阻塞项，不能据此宣称正式回归完成。

完成标准：变更文件全集、比较基准和改动说明缺口可追溯，正式回归入口为“就绪”或有具体阻塞清单。

## 2. 建立行为—传播清单

1. **描述改变的行为。** 提取输入输出、错误结果、权限/租户归属、数据约束、事务、时序、事件、持久化、恢复及构建运行行为的变化。行为保持不变的重构也列出需要继续成立的约束。
2. **追踪生产方与消费方。** 查直接调用方，再逐层判断改变是否传递。除 import 外，检查实际存在的 HTTP、IPC、事件、共享存储、配置、生成代码、资源、提示词/skills 与进程或产物边界。依赖图和历史覆盖只提供候选；既检查读方，也检查会生产新输入的写方。
3. **给出停止边界。** 对每条路径说明下一层依赖的行为为何保持成立，并指出代码、契约或边界测试证据。签名相同不代表权限、顺序或失败语义相同；被依赖也不意味着所有行为均受影响。删除、改名时结合基准版本查旧调用和测试。
4. **处理未知。** 先调查缺失的边或契约。仍无法限定时扩大到可能受影响的模块；跨领域传播仍无法限定时按项目规则升级全量，并报告原因。

范围与后果分别判断：受影响消费方数量决定覆盖广度，失败会违反的关键约束决定验证深度。文件数量、目录数量和风险分数不能单独决定全量。

完成标准：每个变更文件都归入至少一个行为/约束，或有“不改变可观察行为”的依据；每条候选传播路径都有继续、停止或未决结论。

## 3. 映射用例并确定范围

复杂变更建立矩阵，小改动可用等价清单：

| 改变的行为/约束 | 受影响消费方与停止依据 | 选中的用例或检查 | 选择理由/层级 | 结果或缺口 |
| --- | --- | --- | --- | --- |
| 每项一行 | 记录实际传播路径 | 使用稳定用例定位 | 直接、消费方或阶段门禁 | 执行后填写 |

本轮集合为：**直接影响用例 ∪ 受影响消费方用例 ∪ 当前阶段强制核心/全量集合**，重叠项只执行一次。

- 每项受影响行为选择能观察真实边界的最低必要成本检查；需要数据库或跨进程语义时保留该层证据。类型检查、生成一致性和构建检查按改动另选，不能代替运行行为验证。
- 全量只用于项目约定的发布/定期节点、明确要求、已确认的广泛影响或无法收敛的高影响未知。公共权限、事务基础设施、运行机制和大规模架构语义变化是升级信号，具体条件由项目地图定义。
- 纯说明文档且不影响程序/Agent 行为时做文档检查。被程序或 Agent 消费的配置、提示词和 skill 按实际消费关系判断，不能仅按扩展名免测。
- 没有对应测试时，在任务授权内补有效回归，否则记录缺口；“未选到测试”不等于验证通过。

完成标准：除独立阶段门禁外，每项选择都能反向映射到影响清单；每项影响都有检查或显式缺口，无关用例不因同目录或历史习惯被打包加入。

## 4. 编排并执行

1. **核对选择。** 检查脚本和配置，确认命令实际选中计划中的测试并保留必要前置。可用 runner 的 list/dry-run 核对文件与用例；无匹配或空结果先调查路由，不把成功退出视为覆盖成功。
2. **保留筛选语义。** 合并同一 runner 的重复选择时，检查文件筛选与名称筛选的组合规则。例如核心使用 `-t`、模块需要整文件时，直接拼接文件并沿用核心 `-t` 会漏掉模块用例；此时分开执行或调整筛选并消除重叠。
3. **安排前置与并行。** 把构建、部署、数据、账号和依赖准备纳入计划。只有数据隔离、共享资源和输出目录允许时才并行；相互污染的任务串行。成本按准备、执行、阻塞等待、复测和清理计算，不只看单用例时长。
4. **控制重跑。** 相关代码、依赖、配置、测试和环境未变且已有可定位证据时才复用结果；新改动后重跑证据失效的范围。保留首次失败证据并调查原因，不能反复重跑直到绿灯后隐藏失败。

完成标准：实际选择集合与计划一致且非空，必要前置与资源约束已处理，所有失败、未执行和未决项均被保留。

## 5. 判断出口并交付证据

满足计划中的必选项、没有未处理的新改动或失败，且项目规定的核心项全部通过后，才能判定回归完成。已知问题能否带风险发布由项目规则或授权人员决定；环境、真实外部服务、真实平台和分发验证缺什么就报告什么。

小改动用几句话，复杂变更用矩阵，至少说明：

- 比较基准、工作区范围及改变的行为。
- 受影响消费方、停止传播依据、选择的范围及独立阶段门禁。
- 命令、实际选择/执行结果，以及尚缺的测试、环境或未决证据。

明确区分“计划”“仅核对选择”“实际通过”“未执行/失败”。需要评估效率时，记录准备、执行、阻塞等待和复测耗时，并在同等发布频率下观察回归缺陷变化；没有测量数据就不承诺提速比例或质量不变。
