# UI design

让用户看清当前状态、找到下一步并完成任务。按本次改动的规模应用以下原则；局部修改聚焦受影响的组件和流程，沿用项目既有的组件、视觉规范和业务术语。

## 先确定任务

- 明确当前使用者、要完成的任务、所处状态，以及操作成功后的结果；据此决定展示哪些信息和操作。
- 参考现有相邻页面和用户提供的设计。技术实现遵循目标目录的 `AGENTS.md` 及相关框架、组件库约定。
- 根据任务决定信息密度：用户操作流程突出当前步骤；后台列表和详情保留便于查找、比较的业务数据。

## 用结构表达操作逻辑

- 通过位置、分组、间距和视觉权重区分当前任务、必要信息与辅助内容。让当前任务的主要操作清楚可见，次要操作保持可发现。
- 按用户执行顺序组织表单、步骤与反馈。出现需要反复解释的操作时，先检查控件命名、默认值、分组和操作顺序。
- 为卡片、边框、徽章和颜色赋予明确用途，例如划分独立内容、表达状态或突出操作。简单内容可直接排版，按信息关系选择容器。
- 按需处理本次改动涉及的加载、空数据、成功、失败与不可用状态。错误反馈说明发生了什么以及如何恢复；不可用操作在附近说明解除条件。
- 保持可读字号、清楚的标签、足够的对比度和触控空间。通过内容取舍与布局调整减轻拥挤，保留键盘操作和焦点提示。

## 让文字出现在需要的位置

- 每段文字应帮助用户识别对象、做决定、完成操作或理解结果。删除重复标题、复述按钮的说明，以及没有具体信息的宣传语。
- 使用用户熟悉的业务语言。技术实现细节仅在有助于用户决策或解决问题时展示。
- 辅助说明放在对应字段或操作附近；仅部分用户需要的补充内容可折叠或通过帮助入口查看。依据使用频率安排信息，避免为了减少字数增加无谓操作。
- 在确认操作前明确展示相关费用、使用限制、前置条件和重要后果；这些信息应直接可见，兼顾移动端和键盘使用。
- 保留必要的字段标签、格式要求、错误原因和恢复方法。精简说明后，用户仍应能识别控件并完成操作。

### 示例：租赁确认

直接展示游戏、租期、价格及“确认租赁”。把确实影响本次租赁的限制放在确认操作附近。删除没有具体信息的“智能便捷，轻松畅玩”等介绍。若用户仍需阅读大段流程说明才能下单，先检查操作顺序与信息组织。

## 完成前检查

- 从用户视角走通受影响的主要路径：当前状态是否清楚，能否找到下一步，出错后能否继续。
- 逐段检查新增说明：删去后是否影响识别、决策、操作或结果理解？没有影响就删除；存在影响则放到用户需要它的位置。
- 涉及布局、样式或交互时，使用可用的浏览器预览验证实际渲染和相关交互；按受影响页面的使用场景检查窄屏、长内容与相关状态。文案修改检查换行与布局。
- 报告实际完成的验证；无法预览时说明尚未验证的视觉或交互部分。
