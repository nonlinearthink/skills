# 应用项目回归策略

用户已显式要求整理项目回归体系。先通过宿主可用的 skill 机制加载 `regression-testing-strategy`，把它作为测试资产、风险分层、阶段门禁、执行策略和效果评估的唯一规则来源。若该依赖未安装，提示安装同组 `regression-testing-strategy`；在加载前不要写回。

优先在项目原生用例管理系统、文档和测试代码中整理，避免另建影子清单。用户调用本 skill 不等于授权删除或批量改写：先交付可审查的处置清单，只在确认的范围内写回；已有发布门禁需要变更时单独取得授权。

## 1. 确定整理边界与事实源

读取仓库指南、现有用例库、手工测试文档、测试文件与配置、当前需求、发布规则和已有测试地图。

明确本次覆盖的产品能力与版本、手工/自动化用例及存储位置，记录不可访问的来源。区分只读盘点、建议处置和允许写回的范围；事实不足的项目标为待审。

完成标准：整理范围、事实源、不可访问信息、允许写回的内容和需要另行批准的策略变更都明确。

## 2. 建立测试资产清单

使用 [测试资产清单模板](../regression-testing-strategy/references/test-case-inventory.md)，按 `regression-testing-strategy` 的字段要求记录每项用例。自动化测试按实际断言保护的行为归纳，不把文件机械当成一个用例，也不把多个独立行为无依据合并。

完成标准：盘点范围内每项用例都有稳定定位和行为记录；每条当前核心业务链路都有覆盖定位或显式缺口；未知事实均有标记。

## 3. 逐项给出处置

按策略选择保留、合并、改写、调整层级/频率、淘汰或待审，并记录理由。合并和淘汰逐项证明独特约束已被承接，或对应能力确已失效；无法证明时保持待审。

覆盖缺口单列为新增候选。只有任务明确包含测试设计或实现时才补入用例库或测试代码。

完成标准：每项已盘点用例都有处置和证据；每项合并/淘汰都有覆盖审计；所有新增候选都与既有覆盖区分。

## 4. 组织回归集合并评估自动化

按项目风险定义核心、模块和全量回归：核心集去重并对应具体发布决策，模块入口按业务能力与契约组织，全量边界覆盖当前有效、受控的用例。需要定期抽样或保留人工/探索性验证时，记录各自边界。

评估自动化候选及保留人工的理由，记录常规回归集的环境、数据、账号和共享资源要求。自动化建议不等于实施，只有任务包含实现时才编写或迁移脚本。

完成标准：每项有效用例都有优先级、回归层和执行频率；每项核心用例有发布风险理由与稳定定位；每个自动化候选都有收益和维护依据。

## 5. 整理阶段门禁与项目测试地图

按日常修改、普通合并、发布/定期检查整理必需集合、升级全量条件和例外批准来源，记录回归入口、出口及独立外部验证。保留已有更严格要求，不用本次整理单方面改变发布政策。

使用 [项目测试地图模板](../regression-testing-strategy/references/project-test-map.md)，写入固定核心清单、模块传播入口、执行命令与资源约束。命令和稳定选择器从实际脚本及 runner 配置核对，可用 list/dry-run 验证路由非空；建图本身不要求执行完整回归。

完成标准：每个阶段都有必需集合、升级条件和例外来源；每项核心与模块入口可定位；每条命令经过选择核对或有明确缺口；地图与处置清单一致。

## 6. 按授权写回并交付审计结果

把确认后的内容写回项目原生事实源和测试地图，保留原 ID 到新 ID、合并或替代用例的追踪关系。未获写回授权时交付建议清单，并明确“仅建议，未修改”。

交付至少包括：

- 盘点范围，以及保留、合并、改写、调整、淘汰、待审和新增候选的数量与明细。
- 最小发布回归集、模块索引、全量边界和阶段门禁。
- 合并/淘汰的覆盖证明、未覆盖风险和准备缺口。
- 自动化候选与保留人工的理由。
- 实际写回位置、未批准的变更和仍需决策的事项。

需要评估长期效果时，按 `regression-testing-strategy` 记录真实基线和后续观察；没有数据时只报告本次整理事实。

完成标准：每项批准的写回都可定位并保持一致，每项未批准或待审事项都有明确状态，交付能够区分实际修改与建议。
